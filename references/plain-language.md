> **Nontechnical companion / English overview.** Every final technical Markdown document has an identically numbered companion in the stable `大白话解释/` folder. Use the reader's language, explain why, before/after, relevant analogy, annotated steps/diagram, verification, failure cases, risks and jargon. Preserve exact test/acceptance status. Static readability validation cannot prove a human understood the content.

# 大白话解释：一份技术文档必须有一个可追溯的易懂副本

## 强制规则

- 每份**正式**技术 MD 都必须在 `<方案目录>/大白话解释/` 中有**同名、同编号** Markdown 副本，另生成同名 `.html`（只在大白话目录）。适用于方案、用例补充、评审报告、实施/验收记录、手动验收等所有交付 MD；不生成没有技术来源的孤儿解释版。
- 初版方案需**先在会话展示**（不称最终）；需要保存工作中的草稿时只可存当前方案目录 `.drafts/`，不得将其当作正式交付。草稿不用注册编号，完成后应清理。
- 大白话版内容**由 Agent 依据技术版真实内容重新解释**：逐步讲“为什么做、改哪里、怎么判断通过、失败如何处理、会影响什么”，不是复制技术版、空洞宣传或纯 AI 摘要。
- 图解：首选 Mermaid 的 flowchart / sequenceDiagram，若场景简单可用 Markdown 表格+**图解**（如文本方框/箭头），图片仅允许真实截图、经授权的用户素材或实际生成且可落盘的图片；**不得伪造截图或图片证据**。
- 若文件包含执行状态 `BLOCKED`、`未执行`、`未通过`，大白话版必须同样明确标识；失败不能美化为成功。关键数字、范围、风险、限制、版本、命令和证据链接不得改变。
- 大白话版不得包含凭空编出的生产账号、端口、真实测试结果、时间或可点击但不可用的交互控件。
- 技术 MD 必须遵守 PlanShip 自带的普通 Markdown 规范；若 `gen-ui` 已在当前宿主加载，则使用它的适用规范；大白话 MD 也一样，普通 IDE Markdown 预览不依赖 ChatGPT 私有 UI。
- 对过大文档不要生成繁复的装饰性流程图；一张主流程图加关键步骤就足够。**不要为做漂亮图而增加业务设计。**

## 最小结构

````markdown
# <原文件标题>：大白话解释

## 这次要解决什么
普通用户能理解的背景、目标、非目标

## 怎么做／图解
```mermaid
flowchart LR
  A[现状] --> B[最小改动] --> C[真实测试] --> D[用户复验]
```

## 验收时怎么判断
真实输入 → 能看到的预期结果；需要的话给旧功能回归步骤

## 当前状态和注意事项
严格对应技术版的测试状态、未解决风险与限制。
````

该结构仅作说明，实际文档不需要机械复制所有模块；必须与每个原文件类型对应，例如手动验收大白话版要逐条解释真实可执行的 MTC 步骤。

## 版本关联

`scripts/doc_registry.py publish` 会自动加入 `关联技术原文 SHA-256`，并在索引中登记技术 MD、大白话 MD 和大白话 HTML 的哈希。任一技术文件或解释版被手工改动，后续 `validate_docs.py` 和最终验收必须失败，直到两份重新同步发布。

**限制**：机器只能校验配对、哈希、部分状态词一致，不能完全判断两份 Markdown 的语义是否一致；Agent 在发布前需实际阅读逐章核对。


## 事务恢复与大白话一致性

三格式发布发生错误时，报告“发布失败，已恢复旧版”或“待恢复，BLOCKED”，不要只报告“成功”。执行 `doc_registry.py recover` 前先核查是否有人工改动。解释版的业务测试状态必须与技术版一致；静态断言校验通过不代表业务人工验收通过。

## v2.4 可读性红线和五问审查

面向非技术人员的解释不能只是将“事务、幂等、回归”等词换成更短的专业词。必须从使用者角度重新组织：

1. **一句话讲清楚**：不超过两句，回答“为谁解决什么问题”。
2. **原因和前后对比**：实际场景解释“旧行为、期望新行为、不变的行为”。
3. **贴切生活类比**：类比必须指出对应关系和不等同之处，不得将类比当作测试事实。
4. **图配解释**：流程图节点最好为用户行为（打开、发送、查看、失败提示）；箭头与失败分支必须有文字说明，复杂图不必多。
5. **手动操作和风险**：每一验证步骤写“准备什么→点哪里/调用什么→输入什么→应该看见什么→失败怎么办”，保存业务测试状态。
6. **专业词小词典**：术语允许出现，但第一次使用附近要解释。文档要帮助开发人员和非技术人员快速沟通。

使用 `python "<SKILL_ROOT>/scripts/plain_quality.py" --technical "<技术版.md>" --plain "<大白话.md>"` 进行基础静态检查。`doc_registry.verify_file` 也会强制调用同一检查；未通过不得最终交付。

**五问人工式复核**：一个没有项目技术背景的人，是否能答出为什么要改、改前改后哪里不同、图的每步什么意思、失败时怎么办、如何实际验收？不能回答则继续修改。Agent 可以自行审查，但不能冒充真实受访者；想验证真人理解需要用户实际试读。

## v1.3.1 说明：结构通过 ≠ 语义准确

可选 `plain_quality.py` 自动检查结构和显式业务概念，并拒绝部分“只把业务词塞到括号里的关键词堆砌”。它的无错误结果明确为 `STRUCTURE_PASS_SEMANTIC_REVIEW_REQUIRED`，不能写作 `SEMANTIC_PASS` 或 `READER_VALIDATED`。独立复核者应逐个业务场景确认原行为、目标行为、异常恢复及可照做的验收步骤。只有实际非技术人员试读并反馈理解，才能单独记录读者验证；Agent 模拟读者不算真人验收。

## 业务相关性锚点（v1.3）

技术版每份正式 MD 应标注一行 `核心业务概念：历史消息，冷库，归档`（替换成真实业务词）。大白话副本必须逐一正确解释这些概念，并在前后对比、流程图和验收步骤中对应同一业务行为。

可选 Python `plain_quality.py` 对显式概念进行确定性文本覆盖检测；未标概念、缺少概念或只堆砌空模板均返回 `REVIEW_REQUIRED` 或阻断。**文字出现不等于语义正确**，最终仍需逐段独立审阅；没有 Python 时则人工完成该对应检查并说明自动校验未执行。


## v1.3.3 大白话 HTML

HTML 只作为**原大白话 Markdown 的离线可视化副本**，严格遵循 `gen-ui` 的信息呈现与证据诚实原则：清晰标题、移动端友好、表格可滚动、风险及未验证状态清楚可见、没有外部脚本。未启用任何可信图形渲染器时，Mermaid 保留为可读的文本结构及解释，不会伪装成已经渲染的交互图。

每份正式大白话 MD 对应同名 `.html`；技术目录不生成 HTML。工具可选：`doc_registry.py publish` 自动生成；`doc_registry.py sync-html` 安全补全旧版已登记 Markdown。遇到已有 HTML 但无正确索引记录时停止，不覆盖。`verify` 会校验 HTML 哈希与 Markdown 生成结果。Python 未安装时，可通过宿主原生文件操作生成等价 HTML，必须如实说明未验证自动事务原子性。详情见 [HTML 交付说明](../docs/plain-html.md)。
