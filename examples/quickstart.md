# PlanShip 使用示例：给 Java 项目增加查询筛选

这是**示例需求和预期行为**，不是在你的真实业务系统上已经执行成功的记录。

## 第一次：只写方案

```text
$plan-ship 方案编写：
给现有 Java 订单查询接口增加按创建日期筛选功能。
不要修改订单创建、支付和退款逻辑。
请先加载 ai-coding-collaboration 与 intelligent-ui，分析当前代码；
结合会话附件和可选的 test-dir，输出初稿，再做两轮实际评审补强。
最终 MD 保存到 .idea/docs/订单日期筛选/，并生成非技术读者可懂的同名解释副本。
```

预期：主 Skill 报告真实来源；没有安装依赖时 `BLOCKED`，不能装作已加载。Agent 只修改方案文档，不改业务代码。技术版写出 REQ、测试用例、边界、失败行为和旧功能不受影响的依据。解释版应能描述“用户选择日期后，订单列表只显示该日期范围内的记录”。

## 第二次：按照方案实施

```text
$plan-ship 方案实施测试验收：
使用 .idea/docs/订单日期筛选/ 中已通过两轮评审的方案。
先检查测试用例缺口，缺口需要先补用例并两轮评审，再实施最小改动。
必须跑真实 Java 单元测试与必要回归，记录测试命令和输出。
不能执行的用例标记未验证。验收满足后输出可照做的手动验收方案与大白话副本。
```

预期：可验证日期边界（起始/结束日期）、非法日期、无数据、历史无筛选查询行为不变；实际项目没有相应测试基础设施时不要写已经通过。

## test-dir 的分支情况

- 需求只涉及输入日期参数，不需要外部文件：无论 `test-dir` 是否存在，都可自动继续，不需要问用户。
- 需求明确依赖一份用户准备的历史订单样本：先检查 `test-dir/订单历史样本.csv`；不存在时说明用途并只询问一次。
- 已有样本但不可读取：明确报告路径和阻断状态，不推测测试结果。

## 大白话示例的表达方式

> 原来的订单列表像一个放在桌上的全部订单本，查上周的订单只能一页一页翻。现在增加一个“日期筛选框”，输入一段时间就只看那几天的订单；下单、付款和退款的流程还是原来的流程。需要检查日期跨月、选错日期和没有记录时页面会怎样显示。

这段解释没有宣称测试成功。如果测试未执行，应明确补一句“目前只是方案示例，真实环境尚未测试”。

## 最终核验

检查技术文档与解释版编号一致、测试日志确实产生、核心需求用例映射准确、Git 只包含本次必要变更，以及报告明确列出尚待用户手动执行的操作。
